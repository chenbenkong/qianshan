# 千山 · A Thousand Mountains

可以自由穿行的水墨山水。

实时光线步进(raymarching)渲染,无任何贴图、无外部资源、无构建步骤 —— 一个全屏三角形 + 一支片元着色器。

---

## 运行

```bash
npm run dev
```

打开 http://localhost:5173 。任何静态服务器都可以,例如 `npx serve`。

## 画质档位

渲染器按帧耗时同时调节内部分辨率与步进预算。也可以用查询参数指定:

| 参数 | 步数上限 | 内部分辨率预算 |
| --- | --- | --- |
| `?q=high` | 220 | 4.0 MP |
| `?q=medium` | 150 | 2.2 MP |
| `?q=low` | 84 | 0.8 MP |
| `?q=auto`(默认) | 190 | 2.4 MP,再由帧耗时收敛 |
| `?px=1200000` | — | 直接钉死内部分辨率(像素数) |

### 为什么按像素预算而不是 devicePixelRatio

一块 3200×2000 的屏、系统缩放 200%,`devicePixelRatio` 报 2。照直取就是 **6.4 兆像素** —— 笔记本核显无论配多少步数都刷不完,而且画面最后还是被合成器放大,多渲的像素纯属浪费。

改成给内部缓冲**设总像素上限**之后,4K 桌面和笔记本的成本就一致了,而强显卡仍然可以往上爬。

## 实测性能

开发机:Ryzen 5 5600H + Radeon 集显(Vega 8),6 核 12 线程,15.4 GB,面板 3200×2000 @90Hz,系统缩放 200%。

真实 GPU(ANGLE / D3D11),全屏 1600×1000 CSS 视口:

| 档位 | 帧率 | 内部分辨率 | 吞吐 |
| --- | --- | --- | --- |
| `?q=high` | 58.6 fps | 1136×710 | 47 MPix/s |
| `?q=medium` | 67.7 fps | 1188×743 | 60 MPix/s |
| `?q=low` | 75.9 fps | 1131×707 | 61 MPix/s |
| `?q=auto`(默认) | **68.3 fps** | 1192×745 (0.89 MP) | 61 MPix/s |

### 一个反直觉的结论:步数几乎是免费的

把分辨率钉死在 1.60 MP、只改步数:

| 步数 | 帧率 | 吞吐 |
| --- | --- | --- |
| 62 | 41.2 fps | 66 MPix/s |
| 116 | 41.7 fps | 67 MPix/s |
| 150 | 40.5 fps | 65 MPix/s |

**没有差别。** 成本几乎全在与步数无关的每像素固定开销上 —— 天空、云气积分、水面、皴笔触、宣纸纤维。

所以步数应该当成画质来用(默认 190),而不是当成性能旋钮。但弱显卡上步数确实要钱,因此超载时**步数与分辨率同时下调**:哪个真正昂贵就砍哪个,收敛速度也不会被拖慢。

### 实测暴露出的三个 bug

1. `resize()` 里重算 `scale`,而每帧都调 `resize()` —— 自适应刚降下去的分辨率立刻被预算上限覆盖,`auto` 卡在 24 fps 不动。分辨率与上限必须是两个独立的量。
2. 编辑代码时 `resize()` 替换命中了自适应降档分支里的那一处,而不是初始化那一处,同样导致降档失效。
3. 云气沿整条射线积分(而不是地形命中距离),在固定轨道相机下不易察觉,换成自由飞行、相机升高后立刻暴露成满屏白。

## 地形碰撞

镜头不能穿进山体。

高度场在 `src/field.js` 里有一份 JS 移植(`terrainH()`),每帧采样 9 点 —— 正下方加半径 7.5 的环 —— 取最高值作为地板。只测正下方是不够的:那只能防止镜头沉入地面,却挡不住旁边更高的崖壁,于是会一头贴上山壁、画面被近距离岩壁糊满。

`field.js` 必须与 `src/shader.js` 里的 `terrainH()` 保持一致。两者的地形统计量是对齐的(中位高度 -22、p90 17、p99 56),不一致的后果是镜头偶尔会切进山脊,属外观问题而非崩溃。

---

## 远裁剪面随高度自适应

`uFar = 380 + min(camY, 240) × 3.2`。

原因:山最高约 95 单位。从 200 单位高空平视时,射线要 2000 单位才够到地面 —— 固定 400 的远裁剪面会让画面只剩天空。裁剪面随高度放开后,高空也能俯瞰全局。

代价是掠射光线会多走几步,不过步进预算本身有上限,超预算的射线直接判为天空,所以不会失控。

## 乐声

**不加载任何音频文件。** 全部由 Web Audio 现场合成:

- **古琴** —— Karplus-Strong 弦模型。噪声激励送入延时线,反馈端接一阶低通(`0.5 × (cur + next)`),高频随时间衰减,弦的包络自然形成。拨弦位置用梳状滤波在激励端制造,得到比吉他更亮、更「木」的起音。
- **五声音阶** —— 宫商角徵羽,以 D 为宫(徵调式)。乐句用加权随机游走生成,偶尔跳进,而不是随机撒音 —— 这样才有旋律的轮廓。
- **泛音** —— 泛音列(2×、3×)随机叠加,音量压得很低,这是古琴音色辨识度的关键。
- **散音** —— 约 16% 概率延长到 5.4 秒的长音,对应空弦。
- **混响** —— 卷积混响的脉冲响应也是程序生成的(指数衰减白噪声,3.4 秒),不是采样。
- **底噪** —— 两个失谐正弦 + 一个三角波构成持续低音,叠 0.055Hz 的慢 LFO;另有带通滤波白噪声作风声,同样受慢 LFO 调制。
- **随景联动** —— 低音滤波器的截止频率跟随飞行高度缓慢开合(240 → 860 Hz),升得越高声音越亮。

浏览器要求用户手势后才能起声,所以第一次交互(点击 / 按键 / 触摸)时才启用;显式静音会记进 `localStorage`,下次不再自动播放。

## 画面是怎么做出来的

### 地形

高度场由四层叠加:

- **主山脉** —— 3 阶 ridged multifractal,频率 `0.0055`、振幅 `150`。斜率约 28°–45°,这是关键:波长与振幅之比决定了山是"陡壁"还是"山"。早期版本波长只有 57、振幅 105,坡度达 75°,渲染出来是一堆被切掉顶部的抽象条纹,而不是山。
- **支脉** —— 更高频的 ridged,提供次级山体细节
- **基座** —— 极低频 fbm,控制整片山脉的起伏与延伸
- **颗粒** —— 单层噪声,给表面微起伏

这些参数不是猜的,是把噪声函数在 Node 里重写一遍、采样 4 万个点、统计高度分位数与坡度分布定出来的。

### 云气与留白

这是水墨的命门。雾不是"加一层白",而是沿视线**积分**出来的:采样点越低、路径越长,累积的雾越浓,于是远山被"洗"进纸白,近山才留得住墨。采样用 `t²` 非均匀分布,近处密、远处疏。

两个必须做对的地方:

1. 积分上限要用**实际命中距离**,不是远裁剪面距离。用后者会让近处的山也一起变灰,整个画面发死。
2. 积分上限要用**地形命中距离**(`tHit`),不是整条射线的长度。否则即使射线在 50 单位处就撞上了山,后面几百单位根本不存在的雾照样会累加进来 —— 相机一升高这个 bug 就暴露成"满屏白"。

### 皴法

山体纹理顺着局部等高线方向生成:取法线水平分量的垂线作为「沿等高线」坐标,让噪声在这个坐标上高频、在高度方向低频,得到顺坡而下的竖向笔触,而不是等高线状的横条纹。叠三层:底皴、细皺、以及少数几道浓墨重笔。

### 水面

解析求交而非光线步进。水体本身几乎是纸白,只保留稀疏的横向墨线(随距离淡出)与菲涅耳加权的山影倒影。水面向远处**直接溶进天空色**,避免地平线出现硬边。

### 飞鸟

鸟群活在**世界空间**,不是屏幕空间 —— 否则你一转头,鸟会跟着在屏幕上滑动。做法是把射线与 `y = 96` 的水平面求交,在交点处按世界坐标画燕形笔触,于是它们有正确的透视,你从任何角度看都是站在空中的一小队鸟。每 41 秒换一次方向与方位。

开篇取「千山鸟飞绝」。

## 技术

- WebGL2,零依赖,零构建,零外部资源(含音频)
- 单 pass raymarching,自适应分辨率、步进预算与远裁剪面
- 宣纸纤维、暗角、墨色微偏朱砂的后处理
- 附带一个零依赖的本地静态服务器(`server.mjs`)

## 已知限制

- 着色器用 `float32` 算世界坐标。里程极大时噪声函数的 `fract()` 会开始损失精度,地表可能出现轻微重复。正常使用不会碰到。
- 内部渲染分辨率是视口的 ~0.75 倍,靠浏览器放大。在 200% 缩放的屏幕上相当于 1.34 倍放大,近距离看会略软 —— 这是 60 fps 的代价,`?px=` 可以手动换分辨率。
